Handbook · version 1.12.0

Sitekeeper

Save a server once - encrypted locally - then double-click it. What opens depends on what you saved: an auto-logging-in phpMyAdmin tab, a real mysql> prompt, or a two-pane file manager that can keep a folder deployed on every save or every git commit. Open as many as you like at once, in tabs, two side by side.

Windows Python 3.10+ MIT licensed 1.12.0 · one-click handover from hosting providers

phpMyAdmin

A browser tab that fills in the login form for you and keeps its own isolated session.

MySQL

A real prompt on port 3306: ASCII result tables, multi-line statements, history, \G. No phpMyAdmin involved.

SFTP / FTP / FTPS

Local on the left, remote on the right: recursive transfers, hash comparison, and folders that deploy themselves.

Sitekeeper was called MySQL Runner until 1.3.0. It stopped being only about MySQL some releases ago and the name caught up. Saved connections come across on first launch.

Installing and first launch

Windows only, 64-bit. Either run the installer, or run it from source with Python 3.10 or newer. 

# from source
python -m pip install -r requirements.txt
python main.py

The master password, or no password at all

On first launch you choose how the vault is protected. Both options encrypt your credentials on disk; they differ in what unlocks the key.

ChoiceWhat happensCost
Master password The key is derived from it with PBKDF2-HMAC-SHA256 and cached in the Windows Credential Manager, so you rarely retype it. Nobody can recover your connections from the files alone - including you, if you forget it.
No master password The key is sealed to your Windows account with DPAPI. The files stay encrypted and are useless on another account or machine. Anyone who can run code as you on this machine can open them. Auto-lock is switched off, since re-unlocking would be instant.

You can switch between the two later in Settings; the stored servers survive either way.

Five ways in, in rough order of how much typing they cost you.

Whichever route, a connection carries: a label, the connection type, host and port (or a phpMyAdmin URL), username and password, optionally a group, an environment level, a starting directory on each side, and - for MySQL - a database and a startup query to run on connect.

Harder-to-reach servers

A connection can reach its server through another saved connection - name a bastion and its stored credentials are the ones used, rather than repeating a host here. Anything stranger takes an OpenSSH-style ProxyCommand, where %h, %p and %r are replaced with the host, port and username.

Connections from your host new in 1.12.0

If your hosting company supports it, you never type any of this. Click Open in Sitekeeper in their control panel and the account appears in your sidebar - right host, right port, right protocol, opening straight into your document root, tinted red if it is production.

You click the button in your panel

Your browser hands Sitekeeper a link. The link contains a single-use ticket and the name of the host that issued it. It contains no password - that is the whole point of the design.

Sitekeeper asks whether that host may add connections

You see one thing at this stage: the hostname. Nothing has left your machine yet, and a name is the only claim a link makes that TLS is about to check. If you did not click anything, or do not recognise the address, cancel.

It presents the ticket over HTTPS

The connection details come back from your provider, once, in answer to the ticket. The ticket is then spent.

You review exactly what is on offer

Every connection is listed with its label, where it points, the folder it will open in and whether it is marked production - before a single credential reaches your vault.

What Sitekeeper refuses on your behalf

A handover link can be sent to you by anyone, so the app treats every one of them as hostile until you accept:

  • HTTPS only, with a certificate chain your system trusts. A certificate that does not check out means nothing is sent.
  • A hostname only - never a bare IP, and never a name that resolves onto loopback or a private range. A link cannot aim the app at your own network.
  • At most two redirects, and never off the host you were shown.
  • A fixed endpoint path, not one the link chooses.
  • An allowlist over what arrives. Settings that could run something - a local command on connect, a SQL script on connect, a folder on your PC - are dropped whatever the provider sends, and the review screen tells you which were dropped.

There is no "always allow this provider", and there will not be one. The confirmation appears every time. Everything before it is a string somebody else wrote; everything after it is a saved credential.

If the browser does nothing

Some browsers refuse custom links, and the scheme is only registered by the 1.12.0 installer. Your provider can hand you the same ticket as a .skc file instead - download it, open it, same confirmation. Or paste the link by hand: File ▸ Add from a hosting provider link…, also on the connection list's right-click menu.

Opening a handover link while Sitekeeper is already running hands it to that window rather than starting a second copy with its own vault prompt.

Hosting companies: the contract you implement is in For hosting providers, further down this page.

Groups, categories, search

Connections are filed by what they are - phpMyAdmin, MySQL and Other (FTP/SFTP) - each heading carrying its count, and empty categories are never drawn.

Give a connection a group of its own (Production, Client A…) and that wins instead. Move to a group… on the right-click menu offers the groups you already use. Drag rows to arrange a group by hand; a group nobody has dragged stays alphabetical, so arranging one does not scramble the rest.

The search box matches hostnames as well as labels, so webhosting.cloudcore.cz finds the account without your remembering what you called it.

Right-click a connection to connect, open a terminal on it, hand it to PuTTY or Windows Terminal, edit, duplicate it (credentials and all), move it to a group, or delete it.

Sidebar and layout

  • Ctrl+B collapses the sidebar to a slim rail that keeps an expand button in reach; Ctrl+Shift+B hides it outright. Its width is remembered, and dragging the divider almost shut snaps it to the rail.
  • Ctrl+Alt+S splits the tab area in two, so you can watch a query in one pane and a file listing in the other. Ctrl+Alt+M throws the current tab to the other side.
  • The app is dark by default. Ctrl+Shift+D toggles the app theme; Ctrl+Shift+W separately themes phpMyAdmin's own pages with the bundled Dark Reader engine, which computes proper dark colours per element rather than inverting.

Environments and the production guard

Mark a connection Dev, Staging or Production. It is one field, and it changes how the app behaves around that server.

dev staging production

On a production connection:

  • its tab gets a red dot and tint, and the transfer pane's edge turns red instead of blue, so you always know where you are;
  • uploads, deletes, symlink changes, commands and watcher syncs all ask first;
  • handing the connection to VS Code over Remote-SSH asks first, because from then on the editor writes straight to the live box;
  • Claude is granted access to it one connection at a time, beside that connection, so deploying to one live site does not arm the rest.

Startup SQL is a separate field: a query run automatically after login, for things like SET NAMES utf8;. It is typed by you and never accepted from an import.

phpMyAdmin tabs

  • Auto-login - fills and submits the cookie login form, and answers HTTP Basic Auth prompts. The mode is auto-detected, or can be forced per server.
  • Per-tab session isolation - each tab gets its own in-memory cookie jar, so the same server can be open twice without sharing a session. Closing a tab discards its cookies.
  • Session cloning (Ctrl+D) - duplicates the current tab to get a second view into the same logged-in session. Inspect a table in one tab while a query runs in another.

The MySQL console

A native connection to port 3306 with the command-line client's behaviour, inside a tab.

  • Bordered result tables, Empty set and Query OK summaries with timings.
  • Multi-line statements ending in ;, and \G for vertical output.
  • Arrow-key history, plus the \c, \s, \r and \q backslash commands. Ctrl+L clears the screen.
  • Queries run on a worker thread, so the window never freezes, and oversized result sets are capped rather than swallowing your memory.

Terminals

Right-click any connection ▸ Open a terminal (or Ctrl+Shift+T) and you get a shell on that server without opening the file manager first. Inside a transfer tab, the Terminal button and Ctrl+T do the same, starting in the directory you are looking at.

It is line-oriented on purpose. That is what lets it remember your commands per server, suggest and complete them, Ctrl+R back through them, and ask before something destructive on a production box. The same menu hands the connection to PuTTY, Windows Terminal, ssh.exe or WSL instead.

FTP and FTPS connections get one too. FTP has no shell of its own, but the server almost always answers on SSH with the same account - which is usually how the files got there. Sitekeeper asks once per connection before doing it, because that does send the saved password to a different service, and then remembers the port you settle on (Edit ▸ SSH port for the terminal).

The dual pane

SFTP, FTP and FTPS connections open a WinSCP-style two-pane view: local on the left, remote on the right.

  • Browse both sides, transfer whole folders in either direction recursively, create directories, rename and delete.
  • One obvious action at a time. Upload and Download sit in the same place always, and whichever pane you are working in decides which is the action: that one is filled blue and says what pressing it would do (▲ Upload 12, with the destination named), the other stays quiet. The server pane carries the same blue on its edge - red on a production connection - so the button and the folder it feeds are visibly a pair.
  • A pill in the corner is connecting then connected, or not connected.
  • "Start here next time" - right-click any folder in either pane to make it where this connection opens. The two sides are remembered separately.
  • Drag and drop, both ways. Drag rows between panes to copy them, and drop them on a folder to land inside it; the target tints as you hover. Hold a drag near the top or bottom edge and the listing scrolls itself. Local files can also be dragged out to Explorer or an editor, and dropped in from either.
  • Back, Forward and a recent list per pane, plus mirrored navigation that keeps both sides on matching directories.
  • Honest folder dates and sizes - a folder shows the newest timestamp anywhere below it and its real total size, instead of the server's own meaningless directory mtime. Sorting by Modified asks for that walk, so folders - which stay above files - are ordered by a date worth ordering by.
  • Symlinks are shown in italics with their target, are navigable, and can be retargeted from the context menu. That is how you switch which release is live.

The transfer queue

A deploy of small files is limited by round trips, not bandwidth. Each file costs an open, a write, a close and a rename however small it is. So the queue runs on six separate connections by default - configurable up to 16 - and the time divides almost exactly by that number.

  • Ask for more connections than the server allows and Sitekeeper finds the ceiling and settles there, instead of failing the transfers into it.
  • Browsing keeps its own connection, so a running queue never blocks the panes.
  • Pause and resume mid-file, cancel one item or all of them, drag rows into the order you want, or push one to the front. Ctrl+Shift+Q shows and hides it.

Safe deploys and undo

  • Nothing is served half-written. Uploads land on a scratch name and are renamed into place - atomically, where the server supports posix-rename - so a live request never sees a partial file.
  • Undo an overwrite (Ctrl+Z). Whatever a transfer is about to replace is copied into a local cache first. The History window lists everything that was overwritten, with a Restore button per entry.

Keeping the previous version means downloading it before the new one goes up, which roughly doubles the time a redeploy takes. It is worth having, and worth knowing about before a large one - Settings ▸ Transfers.

Uploaded files are given your local modified date, which can be switched off in the same place: it costs a round trip per file, and syncs compare content rather than timestamps now, so it only affects how the dates read on the server.

Comparing both sides

F9, Sync ▾, or either pane's context menu.

Sitekeeper digests both sides, rolls folders up from their contents, and marks every row =, ≠, → or ←. The result window can upload or download exactly the files you tick. On SFTP the hashing happens on the server.

Deploy-ignore rules

.deployignore or .gitignore, full gitignore syntax, plus a built-in list: node_modules, vendor, .git, caches, .env.

Rules apply to batch transfers, comparisons and the watcher. Right-click a file or folder ▸ Never deploy writes the rule for you, anchored to that exact path - a folder's rule takes everything below it - into the .deployignore your transfers actually read, and anything already watching re-reads it at once.

.gitignore is read but never written to. What you deploy is not what git tracks.

Watched and synced folders

Watch a folder

The tab notices files as your editor saves them and can upload each one straight away. A file is only sent once its size and timestamp have settled, so a half-written save never goes up.

Synced folders

Right-click a local folder ▸ Sync folder and pick when it should reconcile itself:

TriggerWhat it does
On saveEvery file goes up as your editor writes it.
On git commitThe folder waits for the repository to record a commit, then compares the whole tree with the server and uploads what differs.

A commit is the honest signal for a deploy: it means "this tree is the one I want live", not "this one file changed".

Rules are remembered per connection and armed again next time you open the tab. Synced folders are marked ⟳ in the pane, and Synced folders… lists everything with its trigger. Ctrl+Shift+S syncs the folder you are looking at once, without arming it.

Scope

A rule can cover a folder with its subfolders, or only the files sitting in it - which is how a site root gets synced without dragging every subfolder up with it. Sync the root that way and the loose files at the top (index.php, .env) stay up to date while assets/, includes/ and the rest are left to their own rules. Arm a folder that already has synced folders under it and it picks files-only by itself.

Removals

Deleting a file locally deletes it on the server - but only ever inside a folder that has a rule, and never below its scope. A full sync shows you what only the server has before touching it. Put uploads/, logs/ and the like in .deployignore and no sync will go near them.

Why comparison is by content, not timestamp

A modified time says when git wrote the file, not when its contents were written. After a clone, a pull or a checkout - or with two people deploying one repository from two machines - identical files look newer than the copies already on the server, and every sync re-uploads the whole tree. So Sitekeeper compares digests. On a server with a shell the whole remote side is hashed by one command. Settings ▸ Transfers keeps the old size-and-timestamp behaviour for the case where hashing is too slow and the timestamps can be trusted.

Publishing from git history

Sync ▾ ▸ Git history…

Reads the repository's log and sends any file as it was at any commit: what one commit changed, for putting a single file back the way it was before a bad change, or every file at that commit, for rolling a folder back to a known-good release.

Nothing is checked out to do it. The old bytes are extracted to a scratch folder and uploaded from there, so HEAD never moves and your working copy is untouched.

Editors and VS Code

  • A remote file - right-click it and it comes down as a scratch copy, opens in VS Code, and every save goes back to the server while the tab is open.
  • A remote folder, on SFTP - VS Code opens it on the server itself over Remote-SSH. Nothing is downloaded, and its search, git and terminal are the server's.

VS Code makes that connection itself, so it asks for the key or password rather than taking this app's. On a production connection Sitekeeper asks first, because from then on the editor writes straight to the live box.

Insiders, Cursor, VSCodium and Windsurf work too (Settings ▸ File transfer picks between them), and the local pane has the same entry beside Open in Explorer.

Permissions

Presets (755 / 644 / 400 / 775 …), a checkbox grid and an octal box that stay in step. Recursive, with a files-only or folders-only scope, and a warning before anything world-writable.

The work happens in the app

While Sitekeeper is running, everything Claude does to a server is carried out by the tab that already holds that connection, over a loopback socket:

  • Uploads and downloads become transfer-queue rows - cancellable, rate-limited, and undoable with Undo replace.
  • Deletes go through the tab that owns the shadow-backup journal, so they can be restored from History.
  • Queries run in the SQL console open on that connection, statement and output landing in the transcript, marked as Claude's.
  • Commands run on the connection that tab already has open, so nothing logs in a second time and what Claude ran joins the history you recall with ↑.

Each call waits for the work to really finish, so Claude reports what happened rather than that it submitted something. With the app closed, the server does the work itself and says which of the two it did. Credentials are never exposed through the tools.

The vault

  • A random Data Encryption Key protects every credential. Nothing is ever written to disk in plaintext.
  • The key lives in memory only while the app runs, and is wiped on Lock or idle auto-lock - 15 minutes by default, configurable. Auto-lock is off when there is no master password, since re-unlocking would be instant.
  • Exported .mrx files are encrypted with a passphrase you choose. Keep that passphrase safe; there is no way back without it.

Host keys

The first time you connect over SFTP there is nothing to check the server's identity against, so Sitekeeper shows you the fingerprint and asks - in both SHA256 and MD5 form, because the value you have to compare against is often a control panel that still prints MD5.

Accepted keys are recorded in known_hosts. If a known host's key later changes, the connection is refused rather than trusted. When a server has genuinely been rekeyed, delete its line from that file.

Part two

For hosting providers

How to put an Open in Sitekeeper button next to an account in your control panel, so a customer goes from "here are your FTP details" to a working, saved connection without ever seeing a password field.

Written for the engineers who build the panel. It assumes you can add a button to a page and an authenticated endpoint to your backend, and nothing about Sitekeeper beyond that.

The moment this replaces

A customer who buys hosting gets six facts: a hostname, a port, a username, a password, a protocol and a directory. They open a transfer client and retype all six, usually wrongly, usually into a client that stores the password in something reversible. The first support ticket of the account's life is often "I can't connect".

One click replaces that. And because you know the document root and they do not, the pane opens on their website rather than on bin, etc, logs, tmp and - somewhere down there - their website.

Build the claim ticket. The .skc file is the same backend endpoint behind a different button, so it costs almost nothing once the first is done, and it covers customers whose browser refuses custom schemes.

The claim ticket flow

The link carries a ticket, never a credential. Credentials travel one way only: over TLS, from your backend, in response to a request that presents that ticket exactly once.

Your panel mints a ticket and opens the link

On a POST from the button - never on page render.

sitekeeper://provision/v1?src=panel.example.com&t=<ticket>

Sitekeeper shows the customer your hostname

And nothing else. Not your product name, not the connection count, not a label - anything a link says about itself is something a forged link says just as convincingly.

It fetches the payload from you

A single HTTPS GET to a fixed path on src, with the ticket as a bearer token. You redeem it and burn it.

The customer reviews and accepts

Only then do the credentials reach the vault.

The link

ParameterMeaning
srcThe host Sitekeeper will fetch from. A hostname, optionally host:port. No scheme, no path, no user@.
tThe ticket. Opaque to Sitekeeper. URL-safe printable ASCII, at least 128 bits of entropy, at most 512 characters.

That is the whole link. There is deliberately no url= parameter: a caller-supplied URL in a link anyone can send is exactly the hole this design closes. The only thing shown to the customer before a byte leaves their machine is src, and src is the one thing TLS will verify a moment later.

The endpoint

Sitekeeper derives the URL from src and a fixed path. You do not get to choose the path. 

GET https://panel.example.com/.well-known/sitekeeper/v1/provision
Authorization: Bearer <ticket>
Accept: application/json
Cache-Control: no-store
Connection: close
User-Agent: Sitekeeper/1.12.0 (Windows)

Enforced by the app, none of it negotiable:

  • HTTPS with a valid chain. No self-signed certificates, no exceptions, no plain HTTP even on a port you think is internal.
  • No IP literals in src, and no name resolving to loopback, link-local or an RFC 1918 address.
  • At most two redirects, same host only. A redirect to another host is a failure, not a hop; so is a downgrade to HTTP.
  • At most 256 KB, at most 50 connections.
  • A response that takes more than 15 seconds is abandoned.

Ticket rules

These are your responsibility, and they are the whole security model. The app's checks protect the customer from a forged link; only these protect the account.

  1. One use. Redeem it inside a transaction and burn it. A second GET returns 401, even ten milliseconds later, even from the same IP.
  2. Short-lived. Ten minutes is generous. The customer is standing at the screen; they are not coming back tomorrow.
  3. Bound to the session that minted it. A ticket is proof that this logged-in customer asked, at this moment, for these accounts. It is not a bearer key to the account.
  4. Scoped to what the button was next to. A ticket minted by the FTP page of example.cz returns that account - not every account the customer owns, and certainly not anyone else's.
  5. Minted on POST, never on page render. A ticket that exists because a page was loaded is a ticket in the browser history, in your access log, and in the referrer sent to every third-party script on that page.
  6. Revocable. Password changed, account suspended, customer clicked "that wasn't me" - every outstanding ticket for that account dies.

Which credential to send

The obvious payload is the customer's own FTP password, which your panel already knows. It works, and over a one-time TLS fetch it is defensible. In order of preference:

Mint a dedicated credential for this handover

An SFTP sub-account or a scoped FTP user, created when the ticket is redeemed and named so the customer can see it in your panel (example_cz-sitekeeper) and revoke it in one click without touching the password they use elsewhere. If the machine is later lost or sold, that is one revocation, not a password reset cascade.

Ship a key instead of a password

Generate an Ed25519 pair, install the public half in the account's authorized_keys, and send the private half as private_key. Sitekeeper writes it into its own storage - only after the customer accepts - and points the connection at it. The password never exists.

Send the existing password

Acceptable. If you do, do not also print it on the page next to the button: having built a flow where the customer never sees the password, do not undo it.

Whichever you choose, tell the customer in your panel what happened. "Added to Sitekeeper on 15 Sep - revoke" is the line that turns a credential handover into something they can audit.

When it is not installed

You cannot reliably ask a browser whether a custom scheme is registered. Every technique is a timing heuristic that breaks on the next browser release, and its failure mode - a customer staring at a page where nothing happened - is the one you were trying to avoid. So do not detect. Make both paths visible and cheap. 

<a class="primary" href="sitekeeper://provision/v1?src=panel.example.com&t=TICKET">
  Open in Sitekeeper
</a>
<p class="muted">
  Nothing happened?
  <a href="https://example.com/sitekeeper">Install Sitekeeper</a>,
  then click the button above again.
</p>

Two things make that second sentence work:

  • Re-mint on every click. The customer is going to leave for four minutes to run an installer. Having the button POST for a fresh ticket each time is simpler than a long lifetime, and strictly better.
  • Link the publisher's own signed installer. Do not re-host the .exe on your CDN. A mirrored copy goes stale, loses its signature more often than you would believe, and trains your customers to accept a hosting company's unsigned binary - exactly the habit a phishing page needs them to have.

The .skc file

Serve the same ticket as a file and the URL scheme is not involved at all. It is the two link parameters as JSON: 

{ "version": 1, "src": "panel.example.com", "ticket": "…" }

Serve it as application/vnd.sitekeeper.claim+json with Content-Disposition: attachment; filename="example.cz.skc". The 1.12.0 installer associates the extension, so opening it runs the same endpoint, payload and confirmation.

A working endpoint

Two routes: one that mints a ticket for the button, one that redeems it. PHP because most panels are, but nothing here is PHP-specific. 

// POST /panel/sitekeeper/start - behind your session auth + CSRF check.
function sitekeeper_start(int $customerId, string $domain): string {
    $ticket = rtrim(strtr(base64_encode(random_bytes(32)), '+/', '-_'), '=');

    db()->insert('sitekeeper_ticket', [
        'hash'        => hash('sha256', $ticket),  // never store the ticket itself
        'customer_id' => $customerId,
        'domain'      => $domain,                 // rule 4: scope it
        'session_id'  => session_id(),            // rule 3: bind it
        'expires_at'  => time() + 600,            // rule 2: ten minutes
        'used_at'     => null,
    ]);

    return 'sitekeeper://provision/v1?src=' . rawurlencode(PANEL_HOST)
         . '&t=' . rawurlencode($ticket);
}
// GET /.well-known/sitekeeper/v1/provision
header('Content-Type: application/json; charset=utf-8');
header('Cache-Control: no-store');

$auth = $_SERVER['HTTP_AUTHORIZATION'] ?? '';
if (!preg_match('/^Bearer (\S+)$/', $auth, $m)) {
    http_response_code(401);
    exit(json_encode(['error' => 'ticket_invalid',
        'message' => 'That link is not valid. Generate a new one from your panel.']));
}

// Rule 1: redeem and burn in one transaction. A second GET must lose.
$row = db()->transaction(function () use ($m) {
    $t = db()->selectForUpdate('sitekeeper_ticket', ['hash' => hash('sha256', $m[1])]);
    if (!$t || $t['used_at'] !== null || $t['expires_at'] < time()) return null;
    db()->update('sitekeeper_ticket', ['used_at' => time()], ['id' => $t['id']]);
    return $t;
});

if (!$row) {
    http_response_code(401);
    exit(json_encode(['error' => 'ticket_expired',
        'message' => 'This link has already been used. Generate a new one from your panel.']));
}

$account = account_for($row['customer_id'], $row['domain']);
audit_log($row['customer_id'], 'sitekeeper.redeemed', $_SERVER['REMOTE_ADDR']);

echo json_encode([
    'version'     => 1,
    'issuer'      => PANEL_BRAND,
    'expires_at'  => gmdate('c', $row['expires_at']),
    'connections' => [
        [
            'label'       => $account['domain'] . ' - web',
            'kind'        => 'sftp',
            'host'        => $account['ftp_host'],
            'port'        => 22,
            'username'    => $account['ftp_user'],
            'password'    => $account['ftp_pass'],
            'remote_dir'  => $account['docroot'],   // the field that earns it
            'group'       => $account['domain'],
            'environment' => 'prod',
        ],
    ],
], JSON_UNESCAPED_SLASHES);

Security checklist

Never put a credential in the link. A URL passed to a shell handler lands in the browser's history and its address bar, in your access logs if the page reloads with it, in the referrer header, in the clipboard the moment anyone right-clicks Copy link address, and on Windows in a process command line other processes can read. TLS protects none of that. The endpoint fetch is the only place credentials belong.

Assume every link is hostile until the dialog is accepted. Anyone can send your customer a sitekeeper:// link naming your panel. What stops it is that the ticket is worthless without your backend honouring it, and your backend only honours tickets it minted for a live session - which is why rules 1, 3 and 5 are not garnish.

  • Tickets minted on POST, behind session auth and CSRF protection
  • Single use, burned inside a transaction
  • Expiry of ten minutes or less, enforced server-side
  • Scoped to the one account the button was next to
  • Revoked on password change, suspension and account deletion
  • Redemptions logged with time, IP and what was handed over - and shown to the customer in their panel
  • Rate limited per account and per IP
  • Endpoint returns Cache-Control: no-store and never enters a CDN cache
  • The ticket is in no URL that gets logged, cached, or sent as a referrer
  • environment set to prod for production accounts

If your onboarding depends on the customer not seeing a confirmation dialog, this integration is not the one you want. It appears every time, and there is no allowlist to get onto.

Testing your integration

# Should return the payload exactly once.
curl -sS -H "Authorization: Bearer $TICKET" \
     https://panel.example.com/.well-known/sitekeeper/v1/provision | jq .

# The same call again should be 401 ticket_invalid.
curl -sS -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TICKET" \
     https://panel.example.com/.well-known/sitekeeper/v1/provision

Then the four failures that actually happen in production:

  1. The customer clicks the button twice in a row. Fresh ticket each click, or a clear "already used" message - never a silent nothing.
  2. The customer clicks, installs Sitekeeper, comes back and clicks again.
  3. The account is suspended between minting and redemption.
  4. A label, group or password contains a non-ASCII character, an apostrophe or a space.

The app's half of this contract is one file, mysql_runner/storage/provisioning.py, and it is the authority wherever this page and the code disagree. The v1 in the link and the path is the contract version; a future v2 will be a new path and v1 will keep working.

A list of connection strings

Sitekeeper reads a .txt of one connection per line, Label = url, # for comments, via File ▸ Import from WinSCP or a URL list…: 

# CloudCore Webhosting - example.cz
example.cz - web      = sftp://example_cz:s3cret@web12.cloudcore.cz:22/home/example_cz/public_html
example.cz - database = mysql://example_cz_admin:s3cret@sql12.cloudcore.cz:3306/example_cz_wp
example.cz - pma      = https://pma.cloudcore.cz/

Schemes understood: sftp, ssh, scp, ftp, ftps, ftpes, mysql, http and https - the last two become phpMyAdmin connections. A bare host:port/path with no scheme is read as SFTP. Percent-encode the username and password.

Providers: be honest with yourself about what this file is. It is every credential for that account, in plaintext, in a Downloads folder, where it will sit until the disk is reformatted - and in whatever backup runs over that folder tonight. If you ship it, say so on the page, set Cache-Control: no-store, and treat it as a stepping stone to the ticket flow rather than the destination.

The encrypted bundle

.mrx avoids the plaintext problem - PBKDF2-HMAC-SHA256 over a passphrase you choose, then Fernet - but trades it for a worse one: you now have to get a passphrase to the customer over some channel, and the channel everyone reaches for is the same page or email that carries the file. Use .mrx for a customer migrating their own machines. Do not use it as a provisioning mechanism.

WinSCP

File ▸ Import from WinSCP or a URL list… finds your sessions where WinSCP actually keeps them: the registry for an installed copy, or WinSCP.ini for a portable one, decoding the stored passwords either way. Those passwords are scrambled rather than encrypted, by a published algorithm - importing them into this app's encrypted vault is a step up from where they came from. Export for WinSCP writes either format back out.
